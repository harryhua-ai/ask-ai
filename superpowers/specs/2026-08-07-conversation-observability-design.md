# 对话可观测体系设计

> 对 ask-ai admin 的"运营"三页(业务概览 / 对话审查 / 技术洞察)重做,形成"业务情报 → 单条诊断 → 系统洞察"闭环,支撑业务决策与答案优化(ask-ai-eval skill)。

## 目标

现有 admin 的运营三页定位混乱:概览是空壳(重定向到数据源)、对话审查只有简单列表(无 trace)、分析仪表盘只有内容维度(无技术性能)。本设计按**使用者 + 目的**重新划分三页,从"技术维度分页"转向"使用者目的分页",并建立闭环。

## 整体框架

侧边栏两组:

| 组 | 菜单 | 本次 |
|---|---|---|
| 运营 | 业务概览 / 对话审查 / 技术洞察 | 重做 |
| 配置 | 数据源 / 对话接入 / 模型配置 / 答案覆盖 / 用户管理 | 不动 |

- 现有"概览"(`/`)是空壳(重定向到数据源),填充为"业务概览"。
- 现有"分析仪表盘"(`/analytics`)改名"技术洞察",并入技术性能。

## 三页定位

| 页面 | 使用者 | 核心问题 | 内容 |
|---|---|---|---|
| 业务概览 | 业务/管理者 | 值不值、客户要什么 | 销售线索 / 场景应用 / 产品需求 |
| 对话审查 | 运营(+ eval skill) | 这条答得怎样、为什么 | 单条对话 + trace 浏览 |
| 技术洞察 | 运营/技术 | 系统健康、知识够不够 | 技术性能 + 知识缺口 |

## 业务概览

业务情报视角。从客户对话提炼三块业务信号:

- **销售线索**:commercial 意图对话 = 潜在客户。线索量、趋势、热门咨询产品、转化信号。
- **场景应用**:客户在什么场景用产品(工业/零售/安防/能源...)。场景分布、各场景产品关联。
- **产品需求**:客户反馈/吐槽/功能需求 = 产品改进方向。需求聚类、热度、趋势。

北极星指标(建议):有效线索数(commercial 且非 off_topic 的真实咨询)。待业务方确认。

数据来源(待定,见开放问题):
- 销售线索:意图 = commercial 的对话(已有意图分类)。
- 场景应用 / 产品需求:需从对话内容提取,候选 A 复用 question_clusters + 标签、候选 B LLM 后处理批跑。

热门问题(原 analytics 的 top)归入业务概览——"客户最关心什么"是业务信号。

## 对话审查

单条对话 + trace 数据浏览器,配合 `ask-ai-eval` skill。

- **列表**:摘要(问题 / 意图·置信 / 迷你阶段耗时条 / 标记 / 反馈 / 时间)+ 筛选 / 检索。
- **详情**:对话内容 + trace 全链路(5 泳道:前置 / 路由 / 检索 / 生成 / 输出,含异常重试、流式延迟拆分、召回质量、降级监控)。
- trace 是给人看"为什么答成这样"的辅助,也是 eval skill 评估答案质量的依据。
- 与 eval skill 共享 trace 数据层;skill 在命令行拉数据优化答案,对话审查在 admin 浏览/定位同样数据。

不做:人工质检标注 / 流转 / 状态(答案优化由 eval skill 负责)。

## 技术洞察

系统健康 + 知识缺口。两个 tab 按信号归属严格分工,不平铺,做"主信号 → 因果/归因 → 支撑"分层。

- **技术性能 tab**(系统跑得快不快、稳不稳):
  - 主信号:**P50/P95 趋势**(双段柱,P95 整柱 + P50 底段,一眼区分长尾恶化 vs 整体退化;含告警基线虚线 + y 轴)。
  - 系统链路因果组(沿链路逐层下钻):① 慢在哪(各阶段 P50/P95 + 正常区间参照,超标标橙)→ ② 什么异常(LLM 超时/降级/其他,纯系统异常)→ ③ 降级到什么(降级链路图:正常→降级节点,有因果)。
- **知识缺口 tab**(知识够不够、准不准):
  - 主信号:覆盖缺口聚类(按类型:拒答 / 召回空 / 低相关,带来源归因"← 来源")。
  - 归因 + 入口:来源质量归因(eval 准确率三级判色)+ 澄清漏斗(问不清的入口,尾部未命中计入缺口)。
  - 支撑:缺口趋势。
- **跨 tab 归属规则**:检索召回为空归知识缺口(作为 miss 类型),不进技术性能异常分布;澄清漏斗归知识缺口(尾部未命中是知识问题)。
- KPI(顶部 4 卡):P95 总耗时、异常率、retry 率、失败率,带基线 + 告警阈值 + 环比;标清包含关系"失败 ⊂ retry ⊂ 异常"。
- 下钻:KPI 卡 / 阶段行 / 趋势柱 / 缺口行 / 降级 都可点,带筛选参数跳对话审查。

## trace 数据层

单独 trace 表,1 conversation : N trace。

```
traces:
  id, conversation_id, prev_trace_id, turn_index,
  type (rag / clarify / reject_short),
  stages jsonb, total_ms, intent, confidence, config_snapshot
```

- 一轮 = 一个 trace(user 输入 → assistant 回复,含一次 RAG 或一次澄清追问)。
- `prev_trace_id`:串多轮,第二轮明确继承第一轮 context。
- `type`:`rag`(正常生成)/ `clarify`(触发澄清追问,不走 LLM 生成)/ `reject_short`(off_topic / <min 短路)。
- `turn_index`:轮次,便于按轮查。
- `config_snapshot`:阈值 / model 版本,改配置后老 trace 仍可对照。
- 采样:正常对话记摘要,异常 / 有反馈 / 抽样的记全 trace(控写入开销)。
- 基准:每阶段记正常区间(P50/P95),数字带参照。

conversation 表保持原样,不塞 trace;trace 表 1:N 关联。

## UI 联动

对话审查内部:列表摘要(迷你阶段条,扫一眼定位异常)→ 详情 trace(全链路)。

业务概览 / 技术洞察:下钻入口 → 跳对话审查(带筛选)。

## 三页闭环

```
业务概览(业务情报)   → 发现线索/需求趋势
   │
   ▼
对话审查(单条浏览)   → 看具体对话 + trace
   │
   ▼
技术洞察(系统+知识)  → 看系统健康/知识缺口
   │
   └─→ eval skill 优化答案 / 补知识 → 回业务概览看趋势
```

## 与 ask-ai-eval skill 的关系

ask-ai-eval skill(位于 camthink/skills/ask-ai-eval/,数据存 Knowledge/Think/ASK AI/optimize/)拉对话 + trace 数据做答案优化。对话审查提供同一 trace 数据层的 admin 浏览入口,两者共享 trace 表。具体拉取字段与是否需要导出入口待确认。
